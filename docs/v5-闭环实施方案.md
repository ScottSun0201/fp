# v5 闭环实施方案（解析现状 + 怎么闭环）

> 分支：reconcile-v2 ｜ 依据：v4-对账闭环设计 ｜ 目的：把"对账没闭环"从方案变成可执行的落地清单

---

## §1 现状解析：现在系统里对账是怎么流转的

把代码跑一遍，实际流程是这样的：

```
上传对账单(8步) ──→ 解析出明细 ──→ ERP核对(阿里云只读)
      │                                │
      │                          ┌─────┴──────────────┐
      │                          ▼                    ▼
      │                   行级校验(逐行)          发票核对(后补)
      │             数量PASS/FAIL·金额PASS/FAIL   金额一致/不一致
      │             占用INFO/OVER·issue_text      发票状态PASS/FAIL
      │                          │                    │
      ▼                          ▼                    ▼
  人工修正明细 ──→ 人工确认行(override) ──→ 确认对账单(approve)
      │                                │              │
      │                                │        status=confirmed
      │                                │        overall=COMPLETED
      │                                ▼
      │                         填写付款记录 ──→ 结束
      └─────────→ 匹配引擎(发票×对账单) ──→ rcn_reconciliation
                                        (full/partial/unmatched + is_confirmed)
```

### 现有的"闭环零件"（能用的）

| 零件 | 在哪 | 现在的作用 |
|------|------|-----------|
| 行级校验 | `stm_statement_allocation`（allocation_status + issue_text） | 每行对账结果：PASS/FAIL/OVER，附问题描述 |
| 人工确认行 | `stm_statement_line_override`（reason/approved_by） | 操作人"人工通过"留痕 |
| 确认对账单 | `stm_statement`（status/overall_status） | 一键 confirmed + COMPLETED |
| 发票核对 | `stm_statement`（invoice_status）+ 发票记录 | 金额一致/不一致留痕 |
| 付款记录 | `stm_statement_record` | 附件/付款/说明，可追溯 |
| 匹配结果 | `rcn_reconciliation`（match_level/is_confirmed） | 发票×对账单匹配留痕 |
| 异常表 | `sys_anomaly`（status open→resolved） | 已建表、已统计"未解决数"，**但没有"解决"动作的接口** |
| 反馈引擎 | `match_feedback` | 人工确认回流匹配加分（存在，但有 SQLite 语法残留炸弹） |

### 断点：为什么"始终没有闭环"

| 闭环要求（v4） | 现状 | 断在哪 |
|---------------|------|--------|
| L1 每笔差异：发现→认领→处理→确认→归档 | 只有"校验结果"（FAIL/OVER），**没有"处理状态"** | 差异没有生命周期：谁处理、处理到哪、怎么处理的、处理完没有，全无记录 |
| L2 任务级：草稿→对账中→待确认→已核销/关闭 | 有 draft→confirmed，但 **ERP_FAILED 也能一键 confirmed** | 没有"所有差异处理完才能核销"的强制，也没有"关闭/作废" |
| L3 月度滚动：本月=上月遗留+新增 | **完全没有遗留概念** | 这个月没处理完的差异，下个月重新冒出来，等于没记 |
| L4 质量闭环：人工结论回流 | 匹配有 feedback，**解析层没有**；行级 override 不回流 | 同样的识别错误、同样的差异每月重复犯 |

## §2 闭环设计：补什么、怎么补

### 核心思路：把"校验结果"升级成"差异工单"

现在系统里"对不上"只是一个红字（FAIL/OVER/不一致），看完了就没了。
闭环 = 每一笔"对不上"都变成一张**差异工单**，有状态、有负责人、有处理动作、有结果，跨月跟踪。

### L1 差异级 —— 差异工单

**新增一张差异表 `rcn_diff`**（统一汇聚所有"对不上"）：

| 字段 | 说明 | 取值 |
|------|------|------|
| id | 工单号 | 自增 |
| statement_id | 来自哪张对账单 | 关联 stm_statement |
| statement_item_id | 哪一行（可空，发票差异无行） | 关联明细 |
| source | 差异来源 | allocation(行级) / match(匹配) / invoice(发票) |
| diff_type | 差异类型 | 数量差 / 金额差 / 单价差 / 无ERP记录 / 超额占用 / 发票差异 |
| diff_reason | 原因分类 | 漏发票 / 未发货 / 单价错 / 数量错 / 其他（可扩展） |
| diff_status | **处理状态** | 待处理 → 处理中 → 已解决 / 遗留 |
| diff_action | 处理动作 | 补票 / 冲销 / 追回 / 忽略 / 其他 |
| diff_owner | 负责人 | 谁在处理 |
| diff_note | 处理说明 | 留痕 |
| resolved_at | 解决时间 | |
| carryover_from | 跨月带入来源 | 上期哪张对账单的工单（空=本期新增） |

**差异清单 = 所有 rcn_diff 的统一视图**：打开一个页面，所有"对不上"都在，筛状态/筛类型/筛负责人。

### L2 任务级 —— 对账单状态机

`stm_statement.status` 从两个值升级为完整状态机：

```
draft(草稿) → processing(对账中) → pending_confirm(待确认) → confirmed(已核销)
     │                                    │
     └─────────────── closed(已关闭/作废) ←┘
```

**关键规则：只有满足下面条件才能 confirmed（核销）**：
- 所有差异工单 = 已解决 或 遗留（遗留必须有原因 + 负责人）
- 不允许"有差异没处理就核销"

这解决 v1 最大问题：**ERP_FAILED 也能一键 confirmed 的漏洞**。

### L3 月度滚动 —— 遗留差异跨月带入

- 每张对账单已有"对账期间"（erp_start_date ~ erp_end_date）
- 新建对账单时（同供应商 + 上期），系统自动把上期 `diff_status=遗留` 的工单**带入本期**，标记 `carryover_from=上期工单ID`
- 结果：**本月差异清单 = 上月遗留 + 本月新增**，一眼看清"这个供应商的历史欠账"

### L4 质量闭环 —— 人工结论回流

| 动作 | 回流到哪 | 效果 |
|------|---------|------|
| 差异处理完（已解决+原因） | 匹配引擎 feedback | 下次同类差异自动识别，不再让财务重复判断 |
| 人工修正识别行 | 解析器反馈表（新增） | 同类对账单下次识别更准 |
| 行级人工确认（override） | 反馈引擎 | 已有，补全 |

## §3 落地清单（按实施顺序）

### 第一批：核心闭环（P0，做完就能用）

| # | 改什么 | 业务效果 |
|---|--------|---------|
| 1 | 建 `rcn_diff` 表 + 生成逻辑（解析/匹配/发票三处自动生成差异工单） | 每笔"对不上"自动成单 |
| 2 | 差异清单页面（management 里加 Tab）：筛状态/类型/负责人，逐单处理 | 财务一眼看到所有待办 |
| 3 | 差异处理接口：认领、填原因、选动作、解决/遗留 | 工单有生命周期 |
| 4 | 对账单状态机改造 + 核销校验（有未处理差异不能核销） | 堵住"带病核销"漏洞 |
| 5 | 遗留差异跨月带入（新建对账单时自动带入上期遗留） | 跨月不丢 |

### 第二批：质量闭环（P1）

| # | 改什么 | 业务效果 |
|---|--------|---------|
| 6 | 差异处理结论回流匹配反馈 | 越对越准 |
| 7 | 解析反馈表 + 回流 | 识别越用越准 |
| 8 | 修 `feedback_engine.py` 的 SQLite 语法残留（`datetime('now','-7 days')`） | 反馈统计接口不再报错 |

### 第三批：管理闭环（P2）

| # | 改什么 | 业务效果 |
|---|--------|---------|
| 9 | 看板：本月对账进度、未处理差异数、超期差异（30天） | 老板一眼全局 |
| 10 | 超期预警（复用 sys_anomaly，补"解决"动作接口） | 差异不会烂尾 |
| 11 | 对账日历/月结提醒 | 到点自动提醒对账 |

## §4 需要你拍板的 3 件事

1. **差异处理动作**：默认 5 类（补票/冲销/追回/忽略/其他），够吗？要不要加"内部调整"？
2. **"遗留"的权限**：谁能把差异标成"遗留"？默认财务即可，需要经理审批吗？
3. **核销硬性要求**：有未处理差异时，是**完全禁止核销**，还是**允许核销但必须备注原因**？（我建议后者，更灵活）
